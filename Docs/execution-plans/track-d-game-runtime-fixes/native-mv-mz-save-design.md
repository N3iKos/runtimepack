# Universal MV/MZ Native Save Adapter — Design Specification

**Status:** Proposed for review; planning only. No runtime or APK changes authorized by this document.
**Scope:** RPG Maker MV and MZ games packaged by RuntimePack, with Forestia (MZ) and The Witch's House MV as representative fixtures.

## Evidence and boundaries

- Forestia MZ serializes objects with `JsonEx`, compresses with `pako`, then calls `StorageManager.saveZip` → `saveToForage`; `loadZip`, `forageExists`, and `updateForageKeys` govern load and slot visibility (`Raw-Game/Forestia1.4.4-IND/js/rmmz_managers.js:549-558,583-632,689-725`).
- The Witch's House MV uses synchronous `saveToWebStorage`, `loadFromWebStorage`, `webStorageExists`; `backup`, `restoreBackup`, and `cleanBackup` also access `localStorage` directly (`Raw-Game/The_Witchs_House_MV/www/js/rpg_managers.js:571-665,722-752`).
- Android currently offers `WebBridge.saveItem/loadItem`, but the active shim only forces `StorageManager.isLocalMode()` false; it does not connect RPG Maker storage to native saves (`android/shell/app/src/main/java/io/runtimepack/host/WebBackend.kt:16-30`, `android/shell/app/src/main/assets/web_shims/runtimepack_web_shims.js:15-29`). `InternalStorageSaveService` writes directly to `filesDir/saves` without atomic replacement (`SaveService.kt:18-49`).
- Forestia's plugin calls `saveSystemAndGlobal()` without awaiting it, and `DataManager.saveGlobalInfo()` does not return its save Promise (`Raw-Game/Forestia1.4.4-IND/js/plugins/inazuma/SaveData.js:613-632`, `js/rmmz_managers.js:64-88`). This is a *potential* ordering hazard, not yet a proven cause of the reported failure.
- The previous APK asset audit validates asset availability, **not** save/load correctness. No on-device save failure stack trace or byte-level reproduction has yet established whether IndexedDB, compression, or plugin ordering caused the historical problem. Do not label these as proven root causes.

## Goal and exclusions

Deliver restart-persistent, correct save/load for both MV and MZ through app-private Android storage. Preserve engine-specific contracts, keep `Raw-Game/` immutable, propagate save failure to the engine, and prevent partial-file corruption. No migration from historical Cordova or RuntimePack saves: development users have no saves requiring preservation. Do not expand the adapter to RGSS, Ren'Py, Tyrano, VNM, or Kirikiri in this phase.

## Components and data flow

1. **Runtime detection and installation.** Extend the existing WebView shim installation used by the game WebView, not the overlay. Detect supported MV functions (`saveToWebStorage` and `loadFromWebStorage`) or MZ functions (`saveToForage`, `loadFromForage`, `updateForageKeys`); install once after the engine defines them and after plugins have had an opportunity to replace relevant methods. Record which functions were wrapped; avoid overwriting plugin logic outside the persistence boundary. If the required native bridge or engine signatures are absent, report a structured diagnostic and retain the original browser implementation instead of pretending a native write succeeded. Test script ordering and plugin method replacement explicitly.
2. **Native save repository.** Expose scoped `read`, `write`, `exists`, `delete`, and `list` operations through the existing `RuntimePackNative` bridge, backed by app-private `filesDir/saves`. Keys are engine-namespaced (`mv/` or `mz/`) and app-scoped. Validate logical slot names against a deliberately bounded character set, reject traversal and ambiguous normalization, and map valid keys deterministically to safe filenames; do not pass arbitrary JS paths to `File`. Write to a temporary file in the same directory, flush and sync it, then replace the destination atomically (e.g. Android `AtomicFile` semantics); preserve the previous valid slot if a write fails. Native errors must be distinguishable from “slot missing”; never silently return an empty success. Deletion and enumeration must use the same key mapping. Existing `WebBridge.saveItem/loadItem` and `SaveService` users must remain compatible; introduce dedicated operations rather than changing unrelated callers' semantics.
3. **MZ adapter.** Intercept the persistence boundary (`saveToForage`, `loadFromForage`, `forageExists`, `removeForage`, `updateForageKeys`) while retaining `saveObject → jsonToZip → saveZip` and `loadZip → zipToJson → jsonToObject`. Encode/decode the actual MZ zip representation losslessly over the string-only JS/native bridge (base64 is an option, but test the runtime payload type and a full byte round-trip before selecting it). Preserve Promise return types and rejection behavior. Initialize the slot index before `forageKeysUpdated()` reports true so `removeInvalidGlobalInfo()` cannot discard valid slots due to an empty startup index. `saveToForage` must resolve only after native storage confirms completion; a failed or missing read must not be converted to a successful empty save.
4. **MV adapter.** Intercept `saveToWebStorage`, `loadFromWebStorage`, `webStorageExists`, `removeWebStorage`, and its direct-`localStorage` backup functions. Preserve MV's synchronous methods and `LZString` transformations; do not send an unbounded uncompressed JSON copy if the native repository can store the compressed representation. Mirror original behavior for absent slots and `.bak` recovery, preserving the prior save when backup/restore fails. Do not route MV through MZ Promise APIs.
5. **Game-specific follow-up only if demonstrated.** Do not patch Forestia's `DataManager.saveGame` by default. First prove a failure after the universal adapter with logs and the slot/global/system state. Only if the slot succeeds but the plugin's non-awaited metadata chain leaves `global` inconsistent, add a narrowly-scoped packaging-time compatibility shim for Forestia's detected plugin/version, with an independent regression test. Never edit the source under `Raw-Game/`.

## Failure handling and verification gates

- **Baseline diagnosis before implementation:** on the currently built Forestia APK, perform fresh save → immediate load → force-stop/relaunch → Continue/load. Capture relevant WebView errors, native bridge errors, native save file existence/size, MZ forage-key visibility, and the states of slot/global/system. State explicitly which step fails; do not infer from the asset auditor's PASS. Use a new save so migration is irrelevant.
- **Unit tests:** Kotlin repository tests for write/read, missing vs corrupt data, unsafe keys, failed write retaining old content, delete/list, and concurrent same-slot writes; JS VM tests for MV/MZ detection, byte-for-byte compression round-trip, sync MV calls/backups, MZ Promise resolution/rejection and `forageKeysUpdated` boot gating. Use a real MZ compression fixture and a real MV LZString fixture as applicable.
- **Integration tests without full APK:** exercise the native bridge and both engine storage entry points using small fixture games, including >5 MB saves, many slots, force-stop/relaunch simulation, and failures (no space, malformed payload). Check that save success is not displayed when native write fails. Benchmark storage latency for large Forestia slots; if synchronous bridge calls cause visible stalls, redesign the MZ write path to async without changing MV's synchronous contract.
- **Final Android gates:** after fast tests pass, test Forestia MZ and The Witch's House MV on MuMu: fresh save, load in same session, force-stop/relaunch/load, repeated overwrites, global/config, MV backup restore, immediate force-stop after save, and failure/error diagnostics. MuMu verification is a release gate, not the inner iteration loop. Record outcomes per engine; never claim that all MV/MZ titles are guaranteed compatible solely from these fixtures.

## Rollout and stop conditions

Implement repository → MZ adapter → MV adapter → fixture tests → APK smoke tests, each behind its own test/review gate and dispatched to subagents only after plan approval. If the baseline shows a distinct cause (e.g. plugin code or a missing startup hook), revise the design before implementation rather than applying speculative storage patches. No engine expansion, signing, publishing, or source-game modification is included.
